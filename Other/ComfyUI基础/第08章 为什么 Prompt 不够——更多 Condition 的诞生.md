# 第08章 为什么 Prompt 不够——更多 Condition 的诞生

## 本章学习目标

完成本章学习后，你将能够：

- 理解 Prompt 的能力边界。
    
- 理解语义信息（Semantic）与几何信息（Geometry）的区别。
    
- 理解为什么 AI 漫剧不能只依赖 Prompt。
    
- 理解 OpenPose、Reference 等控制技术出现的原因。
    
- 建立"导演需求 → Workflow 输入"的设计思维。
    

---

# 8.1 Prompt 能解决什么？

Prompt 的本质是：

> **自然语言描述。**

例如：

```text
A girl is standing on the beach, smiling.
```

Prompt 能很好地表达：

- 人物
    
- 场景
    
- 风格
    
- 情绪
    
- 衣着
    
- 光线
    

这些内容都属于：

> **语义信息（Semantic）。**

Prompt 回答的问题是：

> **画什么（What）。**

---

# 8.2 Prompt 不能很好地解决什么？

虽然 Prompt 能描述：

```text
女孩挥手。
```

但是：

它不能精确表达：

- 手举起多少度。
    
- 身体朝向哪里。
    
- 镜头拍摄角度。
    
- 四肢的准确位置。
    
- 构图布局。
    

原因很简单：

自然语言本身具有歧义。

例如：

```text
美女
```

不同的人：

脑海里的画面完全不同。

因此：

Prompt 适合表达语义。

却不适合表达精确几何结构。

---

# 8.3 AI 漫剧为什么不能只依赖 Prompt？

假设制作 AI 漫剧：

第一镜：

```text
少女站在海边。
```

第二镜：

```text
少女挥手。
```

第三镜：

```text
少女转身。
```

如果全部依赖 Prompt：

模型每次都会重新理解文字。

因此可能出现：

- 发型变化。
    
- 衣服变化。
    
- 人物年龄变化。
    
- 五官变化。
    
- 动作变化。
    

Prompt 并没有告诉模型：

> **第二张图里的少女，就是第一张图里的少女。**

因此：

AI 漫剧无法仅依赖 Prompt。

---

# 8.4 OpenPose 解决了什么问题？

OpenPose 并不是：

图片。

也不是：

Latent。

OpenPose 提供的是：

> **人体几何信息（Geometry）。**

例如：

- 头部位置
    
- 肩膀位置
    
- 手肘位置
    
- 手腕位置
    
- 腿部位置
    

它告诉模型：

> **人物应该如何站、如何走、如何挥手。**

因此：

OpenPose 回答的问题是：

> **动作应该是什么样（How）。**

而不是：

> **人物是谁。**

---

# 8.5 为什么只有 OpenPose 仍然不够？

假设：

仅输入：

OpenPose 骨架。

模型能够知道：

人物姿势。

但是不知道：

- 是男还是女。
    
- 是动漫还是写实。
    
- 穿什么衣服。
    
- 长什么样。
    

因此：

OpenPose：

解决的是：

> **动作一致性。**

并不能解决：

> **人物一致性。**

---

# 8.6 LoRA 能解决人物一致性吗？

很多初学者认为：

训练一个 LoRA。

人物就完全一致。

实际上：

LoRA 的职责是：

增强：

MODEL。

例如：

学习：

- 某种画风。
    
- 某位角色的大量特征。
    
- 某种服饰。
    
- 某种艺术风格。
    

LoRA 能让：

人物越来越像。

但是：

不能保证：

每一张图片：

都是同一个人。

因此：

LoRA：

解决的是：

> **模型能力与风格。**

不是：

> **唯一身份。**

---

# 8.7 为什么需要 Reference？

导演提出新的需求：

> **以后所有镜头都使用第一张图片里的女孩。**

Prompt：

无法唯一描述：

第一张脸。

OpenPose：

只能提供姿势。

LoRA：

只能增强人物特征。

因此：

Workflow 还缺少一种信息：

> **参考对象（Reference）。**

Reference 回答的问题是：

> **长成什么样。**

它提供：

人物外观参考。

从而提高：

角色一致性。

---

# 8.8 AI 漫剧 Workflow 的真正组成

站在导演角度：

导演提出的每一个要求。

最终都会变成 Workflow 中的一类输入。

|导演需求|对应技术|
|---|---|
|画什么|Prompt|
|什么风格|LoRA|
|什么动作|OpenPose|
|长什么样|Reference（后续章节：IPAdapter）|

Workflow 本质上不是：

一堆节点。

而是：

导演需求的数据化表达。

---

# 8.9 程序员视角

从软件架构来看。

每一种控制技术。

其实都在提供不同类型的信息。

例如：

```text
Prompt
↓

语义信息
```

```text
OpenPose
↓

几何信息
```

```text
Reference
↓

人物参考信息
```

```text
LoRA
↓

模型能力增强
```

最终：

这些信息共同参与：

KSampler 的推理过程。

因此：

AI 图片生成：

并不是：

一个 Prompt。

控制所有内容。

而是：

多个模块共同约束最终结果。

---

# 本章总结

Prompt 并不是万能的。

它只能表达：

> **语义信息。**

随着导演提出越来越多的要求：

例如：

- 固定动作。
    
- 固定人物。
    
- 固定构图。
    
- 固定镜头。
    

Workflow 需要不断增加新的控制信息。

因此：

ControlNet。

Reference。

IPAdapter。

Depth。

LineArt。

这些技术并不是为了替代 Prompt。

而是：

> **补充 Prompt 无法表达的信息。**
